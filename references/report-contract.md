# Timon support report contract

## Discord form reference

Match the current form at the user's destination. The following fields describe the reference form, not a guarantee that every deployment uses an identical form. English is the default:

```text
Title of the problem
<specific symptom, optional version; normally under 100 characters>

Operating system
<affected daemon OS; clarify client OS separately if relevant>

Feature or area concerned
<short product surface, such as automatic wakes / Kanban task returns>

Describe the problem
Timon version: <package/daemon version, distinguishing mismatches>
LLM provider / model: <verified provider/model or Unknown; never an account identity>
Steps: <short observed sequence, or clearly labeled proposed reproduction>
Expected result: <user-visible intended behavior>
Actual result: <symptom, scoped count/window and consequence>. Sanitized evidence and details in archive.zip.
```

Use the OS option actually offered by the form; keep distribution and server/client detail in the description/archive. Do not guess an unavailable dropdown option. The reference form allowed up to 5 attachments with inconsistent 10 MB / 20 MB labels. Use a conservative ZIP limit below 10 MB and verify current limits before submission. Never send form data to a bot without explicit authorization.

Keep the description about 100–180 words where that conveys the case, shorter for simple bugs. Use the five labeled lines shown above; do not add a long investigation essay. A missing provider/model is `Unknown`, a genuinely unrelated one is `Not applicable`. Do not borrow a model from an unrelated mission. Screenshots alone cannot prove the daemon's model.

## Archive contents

```text
timon-bug-report/
├── BUG-REPORT.md
├── report.json
├── evidence/                 Only relevant sanitized evidence
│   ├── environment.json
│   ├── log-excerpt.txt
│   └── metadata.json         Optional pseudonymous field-level provenance
└── SHA256SUMS                Generated by the packaging helper
```

Only add evidence files with a clear diagnostic purpose. A small Markdown+JSON report may need no evidence subdirectory. Avoid duplicated reports, raw source dumps and large appendices that force an LLM to rediscover the finding. Never include passwords, hashes of passwords, tokens, cookies, auth files, secrets, database files, full logs, full configurations, transcripts, agent prompts, private knowledge bases, or unsanitized screenshots. Retain the public installer hash when useful; it is not a credential.

## BUG-REPORT.md

Use stable, descriptive headings and explicit labels. Prefer these sections, merging irrelevant ones rather than filling them with invented information:

1. **Summary:** symptom, impact and scope in a few sentences.
2. **Environment:** exact observed versions, affected OS/architecture, install/runtime mode, relevant client/server distinction and provider/model. Unknowns stay unknown.
3. **Preconditions and sequence:** permissions, owner/instance account distinction, prior user actions, deletion/upgrade context. State whether the sequence was observed or proposed.
4. **Expected / actual:** separate behavior, scoped frequency/counts, and consequence.
5. **Evidence and timeline:** cite relative attachment paths, line ranges or JSON pointers; timestamp with timezone. Give each claim enough provenance to be located without reading all files.
6. **Reproduction status:** executed steps and outcome versus proposed minimal steps. Include exact error text after sanitization. Do not start a production workload just to populate this section.
7. **Analysis:** confirmed mechanism versus hypothesis, with confidence and a way to falsify uncertain claims. Static shipped-code observations are not a patch or proof of runtime coverage. Do not claim a specific source commit without evidence.
8. **Acceptance criteria:** observable outcomes and regression scenarios for the maintainer. Include duplicate delivery, retries, restarts and ownership isolation only when relevant to this bug.
9. **Limitations:** unverified claims, inaccessible artifacts, omitted sensitive evidence and observation boundaries.

Severity is a suggestion for maintainer triage: describe impact first. Do not call a whole-service outage P1 when only one workflow fails, assign CVSS without a security analysis, or state business/revenue impact without evidence. Avoid promising a fix; ask for resolution of the observed contract violation.

For multiple coupled findings, use short local labels, explain their relationship and keep one explicit expected/actual pair per finding. Label these as report-local identifiers, not official Timon ticket IDs.

## Machine-readable report.json

This canonical summary complements the Markdown. It should be readable directly by an LLM or a deterministic parser, without proprietary tooling. Required shape:

```json
{
  "schema_version": 1,
  "title": "Concise symptom",
  "observed_at": "2000-01-01T00:00:00Z",
  "environment": {
    "timon_version": "Observed version, or Unknown",
    "operating_system": "Affected OS, or Unknown",
    "runtime_mode": "Observed mode, or Unknown",
    "llm_provider": "Verified provider, Unknown, or Not applicable",
    "llm_model": "Verified model, Unknown, or Not applicable"
  },
  "area": "Affected feature",
  "summary": "Short factual description",
  "expected": "Observable expected behavior",
  "actual": "Observed behavior, scoped counts and impact",
  "reproduction": {
    "status": "observed-existing",
    "steps": ["An observed step or an explicitly proposed step"],
    "limitations": ["Fresh reproduction was not executed"]
  },
  "evidence": [
    {
      "path": "evidence/log-excerpt.txt",
      "supports": "The exact claim this artifact supports",
      "locator": "Lines 3-8; or a JSON pointer or named event"
    }
  ],
  "hypotheses": [],
  "unknowns": ["A material missing fact"],
  "privacy": {
    "manually_reviewed": true,
    "excluded": ["Account identities", "Full logs"],
    "replacements": ["Consistent user and event aliases"]
  }
}
```

Allowed reproduction statuses: `observed-existing`, `reproduced-fresh`, `proposed-only`, `not-reproduced`. `reproduced-fresh` requires evidence of the executed reproduction and its result in the artifacts. If evidence is only the user's account, say so; do not label it independently observed. `observed_at` is the evidence capture/observation timestamp with an explicit timezone, not the report writer's guessed incident time. Optional keys can add severity rationale, linked local findings, count windows, acceptance criteria or source inspection details.

Use consistent aliases such as `USER-A`, `TASK-01`, `MESSAGE-01`, `main-orchestrator`, `retired-project.lead`, `<TIMON_HOME>` and `<LOCAL_ADDRESS>`. Preserve join relationships and nulls. Never include the reverse mapping in the public archive. Keep sensitive exact IDs only in a separate private owner inventory if the user needs them.

## Privacy review and evidence handling

- Start from a narrowly selected dataset. Avoid copying a whole database/log/configuration and then trying to clean it.
- Use existing authenticated CLI/API access without printing or extracting credentials. If a read path would require opening a token, cookie or auth file, use another path or record the missing access.
- Operational SQLite access must use read-only mode and explicit allowed columns. Avoid `SELECT *` on users/accounts/triggers: schemas may include password hashes and webhook secrets. Avoid prompt, payload and transcript fields unless the particular minimal excerpt is necessary and sanitized before output.
- Strip private account labels, emails, public and private host identifiers, real UUIDs, workstation usernames/paths, repository URLs, customer/project identifiers and unrelated task content. Also review filenames, URLs, query strings, traces and screenshot pixels/metadata.
- Keep diagnostic constants that matter: version, error code, durations, field names, null-versus-present ownership, documented loopback addresses and sanitized event timing. Do not alter error semantics while removing identities.
- Text scanners do not validate image pixels, OCR or hidden binary metadata. Review images visually, remove metadata and attach only the minimal crop. The helper supports explicitly reviewed PNGs with no text/EXIF/time chunks; it does not anonymize images.
- Review the *extracted ZIP contents*, not just the source directory. Verify no symlinks, nested archives, hidden files, extra metadata or owner-only notes leaked into the ZIP. Re-run relevant secret scans there and verify file hashes and ZIP CRC.
- Scanner findings must name rules and locations without printing matched values. A clean result is limited to the checks performed. If safe packaging cannot be established, deliver a sanitized text draft and describe what evidence is withheld; do not label a rejected archive ready.

## Timon-specific evidence hints

Discover the active install, service and log locations rather than hardcoding a past host, unit, user, schema or release path. Relevant tools may include `timon update status`, service state, selected `timon doctor` findings, package metadata, narrow daemon-log excerpts, or selected task/mission/message metadata. Do not run every diagnostic indiscriminately: some report account identities, log tails or sensitive configuration. Inspect command behavior first if unsure.

For wake/return failures, preserve separately: distinct original messages, failed spawn attempts, receiving agent, target mission, owning user/instance, source task/creator, expiry and acknowledgement. A batch count or a healthy HTTP endpoint does not prove correct routing or end-to-end delivery.
